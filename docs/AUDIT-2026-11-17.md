**Branch:** `search` (from `full_charity_listing` @ `a036e0f`) — the newest code on the repo.

Ran: `pytest` (322 passed), `ruff check`, `ruff format --check`, `manage.py check`,
`manage.py check --deploy` with production settings, `EXPLAIN ANALYZE` on the listing query,
`pg_indexes` against the dev database, a query-count harness on the real listing page, and an
HTTP sweep of every URL the navigation links to.

**Not checked:** nothing was reviewed in a browser (no browser in this session), so every
visual/accessibility finding below is read from code, not observed. No load test was run. Multi-
instance concurrency (two Gunicorn workers racing on the same row) was reasoned about, not
exercised. No dependency CVE scan was run.

**Severity** is my judgement of cost if left alone: *Critical* = data loss, security hole or a page
that cannot work; *High* = a user-visible defect or a rule the project says it keeps broken;
*Medium* = will cost real time soon or hides a bug; *Low* = worth doing when nearby; *Info* = noted
for the record.

## Real bugs

### B1 — The test suite asserts that eight nav links exist; seven of them 404
**Severity:** High · **Where:** `templates/base.html` (nav), `tests/integration/test_base_template.py:24-33`

`test_home_page_shows_nav_and_local_scripts` asserts each `href` value appears in the HTML, but
nothing in the repository asserts that the href resolves. I requested every nav URL against the real
settings; `/charity/` is the only one that answers:

```text
/charity/            200    /support/help/       404
/charity/add/        404    /tools/              404
/charity/1/          404    /dashboard/          404
/support/report/     404    /accounts/login/     404
/accounts/signup/    404    /accounts/logout/    404 (POST too)
```

So the page a visitor lands on advertises eight destinations and seven lead nowhere — a user-visible
defect, not just missing features (the pages are trivial 404s; the nav promises them). The other
nav tests (`test_logged_in_nav_shows_logout_instead_of_login`) also pass while `/accounts/logout/`
does not exist. The fix: either gate the nav on URLs that exist (D-026 already fixed their *paths*),
or ship the pages; add a test that `client.get(href)` from every nav link returns 200/302.

### B2 — `CharityAdmin.save_model` silently discards any changed field outside `EDITABLE_FIELDS`
**Severity:** Medium · **Where:** `apps/charities/admin.py:15-29`

On a change, only fields in `EDITABLE_FIELDS` (`name`, `tagline`, `description`, `image`) are saved;
everything else changed in the form is dropped, and Django's own save is skipped. Today the form
offers exactly those fields plus readonly `is_visible`, so nothing is lost — but the moment a field
is added to `Charity` and the admin form (say `slug` or a domain/location edit that D-052 already
flags), the admin will report "changed successfully" while the value silently never reaches the
database. This is a landmine, not a bug today: the method should `raise` on a changed field it will
not apply, as `update_charity` already does for unknown kwargs (services.py:49), or fall through to
`super().save_model`.

### B3 — `list_charities` counts and pages in two separate queries
**Severity:** Medium · **Where:** `apps/charities/services.py:214-230`, `repositories.py:206-207`

`count()` and `page()` are sequential queries with no transaction and no snapshot, so a row inserted
or removed between them shifts the window: the same charity can appear on two pages, or be skipped.
For a read-mostly listing this is ordinary and acceptable; it is listed because the repository was
deliberately built to answer "one query per page" (D-050's annotations), which makes it look as if
count and page come from the same snapshot when they do not.

### B4 — The clamp message belongs to the rating group but is emitted by a group-agnostic helper
**Severity:** Medium · **Where:** `apps/charities/filters.py:337-342`

`_adjusted_note` renders "Kept between 1 and 5; using N." for *any* numeric group whose URL value
differed from the applied value. Today only `min_rating` clamps (filters.py:122), so the text is
always about the star scale — but a future clamp on any other group would silently print a
rating-specific sentence. The `adjusted_note` should say *what* was adjusted (a clamped range from
the `Group` entry), or the message should be named for the rating group alone.

### B5 — The search term has no length limit
**Severity:** Low · **Where:** `apps/charities/search.py:122-133`

`from_query` collapses whitespace but never bounds length; the term goes straight into `ILIKE '%…%'`
or a regex for every matching row, so a multi-megabyte URL (Caddy caps request lines, but several KB
is easy) forces an expensive sequential scan and a huge pattern. A `MaxLengthValidator` on the form
or a cap in `from_query` (drop terms longer than, say, 100 chars, the way junk `page` is dropped) is
the fix. Whole-word mode is safe against ReDoS: the term is escaped and has no quantifiers.

### B6 — `record_event` lets an FK violation escape as a raw `IntegrityError`
**Severity:** Low · **Where:** `apps/events/services.py:36-39`

A nonexistent `charity_id` is not a `ValueError` like a bad action is; `Event.objects.create` raises
`django.db.IntegrityError` at the caller with no context. Today every caller passes a real id
(services check existence first), so nothing user-facing breaks; worth a guarded `Charity.DoesNotExist`
when the edit flows land.

### B7 — An admin-added charity is left hidden with no approval record
**Severity:** Low · **Where:** `apps/charities/admin.py`, `apps/approvals/` (empty)

D-038 says every charity gets a `new_charity` approval request, and an admin who adds one creates it
already approved and publishes it. `CharityAdmin.save_model` on add (`change=False`) calls Django's
own save, which defaults `is_visible=False` and creates no request — an admin's charity is invisible
forever unless someone uses the bulk Publish action. The queue (M7/M2 approvals) is the missing
piece; the add path should call the future `submit_new_charity` or at least publish explicitly.

### B8 — `Charity.image` reaches `<img src>` (or `{% static %}`) with no validation
**Severity:** Low · **Where:** `apps/charities/templates/charities/listing.html:51-56`

Two paths, neither validated: a value starting with `http` is used verbatim as an `<img src>`, so
the card will load **any** third-party URL (a tracking pixel or an `http://` image on an `https`
page — mixed content blocked by the browser); anything else goes through `{% static %}`, so
`image="../../secret/…"` renders `/static/../../secret/…`, which servers and browsers neutralise.
Note that `//evil.example/x.png` is *not* caught by the `slice:":4" == "http"` test and is treated as
a repo path, which is the safe outcome. No live hole; the fix is an allowlist (own `/static/` paths
or known hosts) at write time, in the same place the edit flow will validate images (D-052).

### B9 — Repeated `q` parameters silently use the last one
**Severity:** Low · **Where:** `apps/charities/search.py:119`

`?q=a&q=b` searches for `b` with no indication that `a` was dropped. Filters drop junk quietly too
(D-045), so this is consistent — but unlike a filter id, the *first* value here is a real term and
silently losing it will surprise a hand-typed URL. `getlist` + take the last is the fix.

## Data-model and schema gaps

### D1 — No rule stops a member reviewing a charity twice
**Severity:** High · **Where:** `apps/charities/models.py` (`Review`), open question in docs/DECISIONS.md

§8.6 and UC-05 say a member has one review per charity, but `REVIEW` has no unique
`(charity, author)` and no upsert service exists. When the review form lands (§6.2.8), the first
implementation to ship wins this decision; a constraint added after data exists needs a cleanup
migration (N1). This is the oldest open schema question and it is now the only one with user-
visible consequences in this module.

### D2 — The listing's every-page sorts read unindexed columns
**Severity:** High · **Where:** `charities_charity` table; `apps/charities/repositories.py:125-133`

`pg_indexes` shows the only `charities_charity` indexes are `pkey` and
`is_visible_5b8cc7ae`. The default order (`name`) and the `newest` order (`created`) therefore sort
the whole table on every page: `EXPLAIN ANALYZE` shows a `Seq Scan … Sort` (top-N heapsort) even for
a limit-20 read. On 200 rows that is 0.7 ms, invisible; on the real directory it is the two columns
every visitor sorts by, and a btree on `name` (and `created`) makes both orders index-ordered and
pageable with a seek instead of a full sort. Both are one migration each (Platform Lead, D-007).

### D3 — `Transaction.amount` accepts zero and negatives; no rule for `date`
**Severity:** Medium · **Where:** `apps/tools/models.py:18-21`

`amount` is a plain `DecimalField`, so `0` and `-5` are storable, and the maaser calculator
(§6.4.2) will later have to guard against them. `date` is nullable with no semantics (is a
`null` date "today"? "unknown"?). Both are cheap to pin in a check constraint + services rule before
any row exists.

### D4 — `ApprovalRequest.batch_id` is not indexed although the admin queue groups by it
**Severity:** Medium · **Where:** `apps/approvals/models.py:29-33`

§7.1.6's queue groups pending requests by batch; `batch_id` has a model index precedent
(`indexes = [Index(status, submitted_at)]`) but no index of its own, and no unique constraint on
(kind, target), so the same new charity could theoretically hold two pending requests. One composite
index would cover both reads.

### D5 — Admin saves write `""` where the schema says `NULL`
**Severity:** Medium · **Where:** `apps/charities/admin.py:24-29` vs `models.py` (D-013)

Charity fields are `null=True, blank=True`, so the *form* yields `""` for a cleared description and
`update_charity` stores the empty string, while the seed and factories write `NULL`. Two encodings of
"absent" mean `description = ""` and `description IS NULL` never agree in filters, exports or the
future charity page. Decide one (the doc's nullable columns argue for `NULL`; set `"" `→ `None` at
the form boundary) and make the seed agree.

### D6 — The seed gives every approval request its own batch
**Severity:** Low · **Where:** `apps/dashboards/management/commands/seed.py:150-158`,
`tests/factories/approvals.py:16`

`batch_id = uuid4()` per row, so the seed's 15 pending requests (seed.py:97) are 15 unrelated
batches, and the admin queue's "decide the whole batch" flow (§7.1.6) has nothing to bite on in dev.
A handful of shared batch ids — four batches of four, say — would let the first developer of that
screen exercise it.

### M4 — No production traffic ever records a `view` or `link_click` event
**Severity:** High · **Where:** `apps/events/services.py`, `apps/charities/repositories.py`

`record_event` is called only by publish/hide/update (`charity_updated`). Nothing calls it with
`VIEW`, `LINK_CLICK` or `REJECT`, so the only EVENT rows that exist are the seed's `EVENTS = 8000`

listing's `trending` and `popular` orders (D-048, D-050) therefore order by noise in production,

### M5 — `is_visible` is neither enforced in reads nor ever set by an app
**Severity:** High · **Where:** `apps/charities/repositories.py:156-160`, D-042, D-038

`published_only=False` shows every charity because nothing publishes them: the admin queue
(D-038's caller) does not exist, and the admin *can* publish only through a bulk action on a table
that otherwise stays hidden. This is exactly the temporary departure D-042 records, but the audit
notes its bloom: the filters, the search and the sort all read unpublished charities today, so the
day `published_only` flips, the specific semantics of "unpublished charity in a filter/sort" were
never decided. Write the queue first, then flip the flag, then run a "what happens to filtering of
hidden charities" decision.

Documented as D-045's sub-decision, but it is now the only filter group a visitor can see that

### M7 — No email, no Celery task, no chatbot, no calculator, no recommendations
**Severity:** Medium · **Where:** whole repo

`config/celery.py` exists and `CELERY_BROKER_URL=sqs://` in prod, but `@shared_task` appears

listing, which is the audit's point of focus; all of it means the "design doc says SQS+SES" stack

### M8 — No 403/404/500 templates
**Severity:** Medium · **Where:** `templates/`, D-035

D-035 deferred them to "Phase 1", and Phase 1's feature branches exist (`accounts/*`, the listing).
In production (`DEBUG=False`) a 404 or 500 renders Django's stock error page — jarring, and a 500

specified that `500.html` must not depend on context that can fail.

### M9 — `Event.hidden_by_user` is write-only
**Severity:** Low · **Where:** `apps/events/models.py:25`

The column exists (flagging a history item as hidden by its owner, §6.2.10) and is read by nobody:

including hidden ones. When history lands, "popularity" must decide whether a hidden-by-owner view
still counts; worth deciding before `hide_history` writes rows.

## Performance

### P1 — Every listing request reads and renders the full domain and location tables
**Severity:** High · **Where:** `apps/charities/repositories.py:346-356`, `views.py:42-45`

`DjangoFilterOptionsRepository.domains()` and `.locations()` SELECT every row, every page view, then
`filters.html` renders them all into the DOM (scroll-capped, but present — thousands of checkboxes
on a real directory). I measured 6 queries per listing request; the two option reads are 2 of them.
Cache the lists per request (or for a minute), or lazily load an option panel the first time it is
opened. A "type a prefix" search box, as some directories do, would be cheaper still but defeats the
point of checkbox-style faceting.

### P2 — HTMX is render-blocking and unused
**Severity:** High · **Where:** `templates/base.html:8`

`htmx-2.0.4.min.js` (50 KB) loads synchronously in `<head>` on every page. Nothing in the codebase
uses `hx-*` anywhere except the inert `hx-headers` on `<body>`; Alpine (45 KB) at least has `defer`.
`defer` (or moving both to `<body>` end) removes a first-paint blocker with zero behaviour change,
and the `hx-headers` attribute can wait until an actual HTMX interaction exists (D-035 plans the
retry indicator then anyway).

### P3 — No fingerprinted static assets in production
**Severity:** Medium · **Where:** `config/settings/base.py:81-83`, `config/settings/prod.py`

`STATIC_URL` is plain and no `STORAGES` manifest backend is configured, so `{% static %}` emits
`/static/css/site.css` forever. After a deploy, cached browsers and Caddy edges can serve yesterday's
CSS with no way to bust it (the classic "I pushed, why does it look old"). `ManifestStaticFilesStorage`
gives hashed filenames for one `collectstatic` + setting change; `CompressedManifest…` also shrinks
the CSS. This is cheap **now** because `staticfiles/` is not yet a live deployment concern.

### P4 — The listing's one query carries four correlated subqueries and two aggregates
**Severity:** Medium · **Where:** `apps/charities/repositories.py:192-203, 285-296`

The page SELECT annotates `review_count`/`average_rating` (joins) plus `event_count`, `last_changed`
(two subqueries) and, for trending, `trending_score` (a third), all correlated per row, on a table
with no sort index (D2). It is one query, which is the doc's constraint, and it is fine at seed
scale; at directory scale the plan will degrade to a sequential scan with 200–20,000 evaluations of
each subquery per page. The durable fixes are D2's indexes plus limiting options (P1); the *cheap*
fix when it starts to hurt is a summary row per charity (what the doc's derived-value table implies
it would eventually store — that decision should be made deliberately, not by accident).

### P5 — Pagination has no first/last jump and no result count; out-of-range `page` waits for a full count
**Severity:** Low · **Where:** `apps/charities/services.py:216-230` (`Page.numbers`, `page_count`),
`templates/charities/listing.html`

`Page.numbers(window=2)` renders at most 5 links; on page 9 of 100 a reader cannot jump more than 2
pages per click. `Page.total` is computed and then never rendered anywhere (only `page_count` is),
so the page cannot say "1,234 charities" even though it already knows. Also, `list_charities`
computes `page_count` from the full `COUNT` before clamping, so `?page=9999` pays for the scan
anyway; the clamp is correct, the cost is unnecessary. First/last links and a total in the header
would close most of it; skipping the count when `page` is beyond an obvious bound is the micro-fix.

## Code smells and technical debt

### S1 — Three parallel value-object modules repeat the same shape
**Severity:** Medium · **Where:** `apps/charities/{filters,sorting,search}.py`

Each module independently implements: a frozen dataclass of the URL's state, `from_query(query)`,
`query_pairs(value)`, `query_string(value)`, and a `*Form` dataclass for the template. That is
60–90 lines of near-identical plumbing three times, and the `Page` class then juggles three separate
pair tuples (`search_pairs`, `filter_pairs`, `sort_pairs`)
plus three includes (`search_state.html`, `filter_state.html`, `sort_state.html`) that must be
remembered in six forms. A single `PageState` value ("the whole view state") with per-module
adapters would collapse this and remove a whole class of "form forgot an include" bug (the search
work needed exactly that pattern, and it is now doubled — S7 lists the narrow version).

### S2 — The seed command imports the test package
**Severity:** Medium · **Where:** `apps/dashboards/management/commands/seed.py:23`

`from tests import factories as f` puts a runtime import of the test suite inside an installable
app. D-022 blesses the behaviour, not the packaging: `tests/` is not part of a production artifact,
so `manage.py seed --help` would `ImportError` in a deployment that ships `apps/` only, and a
developer reading `apps/` sees a test-only dependency as if it were production code. Either move the
factories to `apps/dashboards/management/commands/_seed_data.py`, or document that the command is
development-only in the packaging story too (a `if settings.DEBUG` guard helps but is checked
*after* import).

### S3 — No error handling and no logging anywhere
**Severity:** Medium · **Where:** whole project

`grep -rn "logging.getLogger" apps` returns nothing: no app has a module logger, and the three
`except` blocks in the codebase (`filters.py:181,199`, `views.py:31`) all swallow silently. Production
`LOGGING` is configured (prod.py:44) but writes only whatever Django itself logs. When the first
500 happens in the edit flow or the review form, there will be no application context (what was
being saved, for which charity). A module-level
`logger = logging.getLogger(__name__)` and a log line in the service layer's error paths is cheap
insurance; the current code has zero.

### S4 — The nav is hand-written URLs in HTML
**Severity:** Medium · **Where:** `templates/base.html:13-30`

Every link is a literal `"/charity/add/"` rather than `{% url 'charities:add' %}`. Renaming or
moving a route (D-009's hyphen conventions are still being applied) breaks the nav silently, and no
test can catch it because the test asserts the same literals (B1). `{% url %}` fails loudly at
render time instead.

### S5 — Loose typing on the filter-options repository
**Severity:** Low · **Where:** `apps/charities/services.py:209-227`, `repositories.py:337`

`list_domains(repository)`, `list_locations(repository)`, `list_rabbis(repository)` and
`filter_form(filters, options, requested)` take untyped arguments, while `list_charities` takes the
`CharityRepository` protocol. `DjangoFilterOptionsRepository` has no protocol of its own, so the
"everything behind an interface" story holds for the listing but not for the sidebar. A five-line
`FilterOptionsRepository` protocol would finish it.

### S6 — Two brand blues and a duplicated rule in the stylesheet
**Severity:** Low · **Where:** `static/css/site.css:33,215,269,283` vs `:124,442,459,506`

`#1a4d8f` and `#1a4f8a` are both used for "the blue" — links/focus in one place, buttons and the
current sort direction in another. Side by side they read as different colours. `.jump__input` is
also declared twice (`site.css:526` and `:541` — a width override in a second block). No CSS custom
properties anywhere, so a brand tweak is a find-and-replace through 562 lines.

### S7 — Three `urlencode` call sites build the same state string
**Severity:** Low · **Where:** `apps/charities/services.py:104-110`, `filters.py:100-112`,
`sorting.py:147-165`, `search.py:160-169`

`Page._state_query`, `filters.query_string`, `sorting.query_string` and `search.query_string` all do
the same join, and `Page` concatenates them by hand in a fixed order. This works because the order
is written once; a fourth module (a date filter, say) must edit `Page` in two places. Part of S1.

### S8 — Factories use random values as defaults
**Severity:** Low · **Where:** `tests/factories/charities.py:74,85`

`ReviewFactory.rating` is `Faker("random_int", 1, 5)` and `HaskamaFactory.importance` similar. Any
test that asserts an *aggregate* (average rating, ordering) without pinning the values is flaky by
construction; today the suites that care set them explicitly, so nothing is failing — the risk is
that the next test author trusts the default. Fixed, obvious defaults (or a documented "pin this")
prevent a 1-in-25 mystery.

### S9 — django-auditlog runs on every request and records nothing
**Severity:** Low · **Where:** `pyproject.toml:12`, `config/settings/base.py:23,43`

`django-auditlog` is a dependency, an installed app and a middleware, so it creates its own tables
in every migration run and wraps every request — while `auditlog.register` appears nowhere, so not
one row will ever be written. DECISIONS.md's open question ("which models get audit logging?") defers
this to Phase 1, which is fine as a plan; the code as shipped is a dependency that costs migration
surface and per-request work for nothing. Either register `Charity` now (D-052's note says that is
exactly the "which field changed" trail the event model cannot express) or leave the package out
until the question is answered.

## Security and deployment hardening

### SEC1 — No CSP, and HSTS preload is off
**Severity:** Medium · **Where:** `config/settings/prod.py`

`manage.py check --deploy` reports one warning on a correct secret: `SECURE_HSTS_PRELOAD` is not
set. There is also no `Content-Security-Policy` anywhere (Django has no built-in), so the app relies
on `X-Frame-Options: DENY` (default), nosniff and autoescaping alone. The templates are CSP-friendly
already (one external script pair, no inline handlers; `hx-headers` is an attribute, not a script),
so a `default-src 'self'` header from Caddy is nearly free and would have been the second line of
defence for B8. Preload is a one-line setting, though it should be decided (not accidental) since
the preload list is hard to leave.

### SEC2 — The CSRF token is written into an HTML attribute on every page
**Severity:** Medium · **Where:** `templates/base.html:11`

`<body hx-headers='{"X-CSRFToken": "{{ csrf_token }}"}'>` exists so a future HTMX call can send the
header. It puts the per-session CSRF secret into the DOM (fine — the form tokens are there anyway)
but, more importantly, it makes every page **cache-unsafe**: any CDN or Caddy cache rule that serves
one visitor's HTML to another hands them a shared CSRF token. No caching is configured today, so
this is a trap for the first person who adds `Cache-Control` to speed up the listing. Remove the
attribute until an HTMX interaction needs it (D-035 plans that work anyway), or use `hx-on::config-request`
to read the cookie.

### SEC3 — `django-admin/` has no lockout, while login will
**Severity:** Low · **Where:** `config/urls.py:11`

The project's own login design (upstream branch `accounts/login`, decision
`D-YOSEF-accounts-login`) rate-limits per client IP with a token bucket and locks out per account
after repeated failures. Django's admin login at `/django-admin/` is a second authentication surface
with none of that, reachable by every staff account. Worth covering
in the same rate-limit middleware or documenting that staff-only access makes it acceptable.

### SEC4 — The dev seed creates `admin` / `admin`
**Severity:** Info · **Where:** `apps/dashboards/management/commands/seed.py:134`

A five-character superuser password. D-030's two guards (DEBUG on, every app table empty) are what
keep this from ever touching a real database, and the seed refuses non-empty databases. Still the
one place a "known default credential" exists in the codebase; its safety rests entirely on those
guards holding.

## Accessibility and user experience

### A1 — Dead links are what a visitor sees first
**Severity:** High · **Where:** B1, M3

Both the nav (7 links) and every card (`href="#"`) lead nowhere. A screen-reader or keyboard user
tabs through eight destination links that announce themselves and then 404, and the card link
announces "charity name" with no consequence. The nav fix is B1; the card fix is the charity page.

### A2 — `aria-disabled` on non-focusable pagination spans
**Severity:** Medium · **Where:** `templates/charities/listing.html:113,131`

The disabled Prev/Next steps are `<span aria-disabled="true">`, which announces "dimmed" on something
a keyboard user cannot reach and cannot act on. Either drop `aria-disabled` there (the styling is
enough) or render a real `<button disabled>` so the state is coherent.

### A3 — No skip link, no nav landmark label, and a heading jump
**Severity:** Medium · **Where:** `templates/base.html`, `listing.html`

There is no "Skip to content" link before the eight-item nav; the main `<nav>` has no `aria-label`
(the pagination `<nav>` does, so the two are distinguishable only by position); and in DOM order the
sidebar's `<h2>Filters</h2>` sits *before* the results' `<h1>Charities</h1>`, so the document outline
starts at level 2 and then jumps up. `<main>` also has no `id`, which is what a skip link would
target. While there: card names are `<span class="charity-card__name">`, not headings at all, so a
screen-reader user navigating by heading finds one heading per page and cannot skim the results.
Four small edits: the skip link, the nav label, h1-before-aside in source order, and `<h3>` for the
card names inside `<h2>Results</h2>`.

### A4 — Only two control types have a styled focus ring; the nav falls back to the browser's
**Severity:** Low · **Where:** `static/css/site.css:214,330`

There are exactly two `:focus-visible` rules in 562 lines (`.filters__options` and `.charity-card`),
and no global rule and no `outline: none` reset. Everything else — the eight nav links, the search
input and its submit, the sort buttons, the pagination links, the jump and page-size inputs —
therefore shows whatever outline the browser defaults to. That happens to be visible on the white
page but is a blue-ish ring drawn on a solid blue nav bar (`#1a4f8a`), which is the least legible
place for it. One global `:focus-visible` rule (and a light variant inside `.nav`) fixes every
control at once and makes the two bespoke rules unnecessary.

## Testing gaps

### T1 — No coverage measurement
**Severity:** Medium · **Where:** `pyproject.toml`

322 tests pass, but nothing measures which lines they reach, so "is the exception path covered?" is
answered by reading. `pytest-cov` + a `--cov-fail-under` in CI (say 85) would make the untested
corners (Django admin actions, `prod.py` guards, seed error paths) visible as numbers rather than
guesses. This audit could not report a coverage figure for that reason.

### T2 — Three tests assert CSS text, not page behaviour
**Severity:** Medium · **Where:** `tests/unit/test_template_contract.py`,
`tests/integration/test_base_template.py:52-64`

`FilterSidebarCssTest`, `test_nav_is_pinned_to_the_top` and the full-width nav test read `site.css`
with a regex. They pass if the *declaration* exists in the file, not if the rule applies to the
element (a later `position: static` override, a media query, or an unused selector all pass). The
intent (catch accidental deletion) is good; the mechanism cannot catch a swallowed selector list at
the same time. A DOM measurement (as the `ux-*` skills do) is the only real check.

### T3 — `tests/unit/test_views.py` is 731 lines in one file
**Severity:** Low · **Where:** `tests/unit/test_views.py`

Five unrelated page contracts (listing, sort, filter, clamp, search) in one 731-line file that now
holds 74 tests. The file is well-written; it is just past the size where a reader can find
the test for a behaviour, and every feature branch edits it (so it conflicts). Splitting per feature
(`test_views_listing.py`, `test_views_sort.py`, …) costs one mechanical commit.

### T4 — Nothing tests the production settings or the Celery wiring
**Severity:** Low · **Where:** `tests/`

`prod.py`'s two `RuntimeError` guards (secret length, allowed hosts) and `config/celery.py`'s app
construction are untested; a typo in the guard condition would only appear at deploy time. Two small
unit tests (import the module with patched env) would cover the highest-consequence settings in the
project.

## Questions I could not settle

### Q1 — Is `maasermart.com` served by Caddy (Django) or by GitHub Pages (`index.html`)?
Both are configured in this repo: `CNAME` names the apex, and the design doc puts Caddy in front of
Django. If Pages answers the apex, the Django app has no root document; if Caddy does, `index.html`
and `CNAME` are stale artifacts. Unverifiable from the code alone.

### Q2 — When `published_only` flips (D-042), do filters, search and sort still read unpublished charities?
Today every read path reads every row. D-045 sub-decided that "the filters apply the same way";
nobody has decided whether a hidden charity is simply absent everywhere or still contributes its
reviews and haskamas to rows a visitor can see (it cannot, being a different charity). One line in
the repository today, a data-semantics question the day the queue lands.

### Q3 — Does the Haskamos filter compare user ids or profile ids?
D-045's sub-decision queries `HASKAMA` by `rabbi_user_id` (the user id) and `RabbiOption.id` is
documented the same way; but §6.2.4's parameter line says "username", and `search_rabbis` (M6) will
read rows from `RABBI_PROFILE`, whose `pk` is a different number. The wiring must not accidentally
hand back `RabbiProfile.pk`. Flagged because M6 is the next small task and its test will not catch
the mix-up unless it asserts what the id means.

### Q4 — Is accent-insensitive search wanted?
N10 records that "chesed" does not find "Chésed". The doc says only "case-insensitive", so the
built behaviour is compliant; whether that is *good* for a directory full of transliterated Hebrew
names is a product call, and N10 already has the `unaccent` fix written down.

## What I would fix first

1. **B1 + M3 + DOC3** — decide the charity URL (D-entry), and either ship the pages behind the nav
   or stop advertising them. This is the only set of findings a real visitor sees today.
2. **D1 + D2** — the review uniqueness constraint (before review data exists) and the two indexes on
   `CHARITY` (`name`, `created`). Both are migrations, both get more expensive every day.
3. **M4** — record a `view` event per charity shown. It is the smallest change that makes the
   trending/popular sorts mean anything, and it exercises the events dependency for real.
4. **DOC1 + P2 + SEC1** — the wrong README (blocks new developers), the blocking 50 KB script, and
   the CSP/HSTS header. Small, independent, all one-file changes.
5. **S1/S7** — collapse the three view-state modules into one `PageState` before the fourth
   (a date range filter is the obvious next one) copies the pattern again.
